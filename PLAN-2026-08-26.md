## Guiding insight

The foundations are strong; nearly every problem is **"a good system was built, then bypassed."**
- Code: every Supabase action auth-derives identity correctly — the Redis path was the lone deviation.
- UI: a solid design system (`components/ds/`) exists but is bypassed by ~217 hand-rolled `<button>`s and two older component generations (`components/ui/` broken shadcn scaffolding + `note-block/*` legacy).

So this is consolidation + cleanup, not a rewrite.

**Storage tiers (critical context):** `source/storage === "redis"` = the **anonymous tier** (LocalStorage UUID token, no auth session — the token IS the credential). `"supabase"` = the **authenticated Cloud tier**. Anything that could leak a Redis token is severe.

## ⬜ F1 — Collaborative editing (NEW FEATURE)

Editable shared notes with per-person permissions + lease-based locking + live "who's editing" presence.
**Biggest item on the board. Depends on P1 #1 + #3 (reliable saves). v1 = Supabase (Cloud) tier only.**

### Permission model (FINAL — Google-Docs style)

- **Link is ALWAYS read-only. No public-editable toggle.** `shared_notes.is_public` only controls whether the link grants VIEW. (A public-edit link = anonymous vandals — rejected.)
- **"People with access" section is always visible** (today it's hidden when public — `sharing.ts:314` only adds readers `if (!isPublic && username)`; lift that so named users can be added in both public and private modes). Relabel the existing add-by-username UI to **"People with access"**, each row a **Can view / Can edit** dropdown; link toggle sits above it.
- Per-person role: new column `shared_notes_readers.can_edit boolean`. No `link_permission` column needed.
- **Key consequence:** editing always requires being a **named, authenticated collaborator**. The public can only read → **no anonymous editors ever** → locking is clean (every editor is a known identity). This is the whole reason the model works.
- **Access matrix:** Can view? owner OR `is_public` OR named-reader. Can edit? owner OR (named-reader AND `can_edit`) — never via public link.
- **Enforcement is server-side:** the save-shared-note action independently verifies edit permission and rejects otherwise; hiding edit UI is cosmetic only.
- Nuances: (a) adding "view" on a public note is redundant-but-harmless (matters if link later goes private); UI nudges toward "Can edit" for public notes. (b) named editors bypass a public note's password/expiry.

### Locking model (lease-based, NOT close-based)

- **Lease, not lock.** Editor client heartbeats every ~15–20s to renew a ~45–60s TTL lease. Heartbeats stop (close, crash, sleep, offline) → lease expires → auto-unlock. **Never rely on `beforeunload`/"note closed"** (orphaned-lock trap). Supabase Realtime Presence drives the live signal; DB lease is source of truth. Lazy expiry check (`lock_expires_at < now()`) on acquire — no cron.
- **Atomic acquire:** single conditional `UPDATE ... SET locked_by=me WHERE locked_by IS NULL OR lock_expires_at < now()`; never read-then-write.
- **Lock is per-session, not per-user** (owner's phone shouldn't block owner's laptop).
- **Owner force-unlock:** if the evicted editor is live → broadcast eviction → their client flushes + goes read-only → then owner loads. If they're gone → owner gets their last autosaved state (last unsaved seconds lost — unavoidable; surface in UX). **Never silently revert the evicted editor's screen** — offer conflict copy or clearly discard.
- **Downgrade (edit→view or stop-sharing) while target is editing MUST trigger eviction** (force-release, flush, flip read-only). Permission control + lock are coupled — build together.
- Editor readonly plumbing partly exists (`[data-readonly]` in globals.css + Milkdown readonly).

### Presence — "who is currently editing" (user-requested)

- Show the current editor's identity to everyone viewing the note: e.g. **"Jane is editing…"** badge (avatar + name) in the editor header and on the read-only shared viewer.
- Driven by the same lease/presence data (`lock_label` = editor's username/display name). For the anonymous tier (not in v1 scope) this would be "Anonymous", never the token.
- When the lock is free, viewers with edit rights see an **"Edit"** affordance; when held, they see **"Locked by X"** + (owner) **"Take over."**

### F1 build order

1. Migration: `shared_notes_readers.can_edit`, lock fields (`locked_by_session`, `lock_label`, `lock_acquired_at`, `lock_expires_at`) — or a `note_locks` table.
2. Server actions: extend sharing for per-reader roles + access matrix; `acquireLock` (atomic), `renewLock` (heartbeat), `releaseLock`, `forceReleaseLock` (owner); edit-permission check on the shared-note save path.
3. Modal→Drawer "People with access" UI (depends on P2 #14) with role dropdowns.
4. Editor wiring: readonly toggle bound to lock state; heartbeat; presence badge; eviction handling.
5. Realtime channel for lock-state + presence broadcast.
